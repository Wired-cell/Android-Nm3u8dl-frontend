USER-REPORTED ERRORS

[ ] 1. FFmpeg launch: "libc++_shared.so not found".
    Change made: Package the ARM64 NDK libc++_shared.so beside FFmpeg; verify APK contains it; use native-library directory for launch.
    Verification: Source/workflow checks added. Requires successful CI build and Android-device smoke test before marking fully resolved.

[ ] 2. FFmpeg launch: "cannot locate symbol OpenSSL_add_all_algorithms referenced by /system/lib64/libsqlite.so".
    Change made: Added a dedicated FFmpeg launcher that resets LD_LIBRARY_PATH to the native-library directory so the app-private OpenSSL 3 folder is not exposed to FFmpeg/system libraries.
    Verification: Source/workflow checks added. Requires successful CI build and Android-device smoke test before marking fully resolved.

[ ] 3. Download start: "mp4decrypt not found" (reproduced by the user's 1.5.0 device test).
    Root cause confirmed from the exact bundled upstream tag v0.6.0-beta:
      - Program.CheckMediaTools() handles DecryptEngine.MP4DECRYPT by unconditionally calling GlobalUtil.FindExecutable("mp4decrypt").
      - It ignores option.DecryptionBinaryPath entirely in that release.
      - GlobalUtil.FindExecutable() searches Environment.CurrentDirectory, the engine directory, then PATH. The app's current directory is files/native, while the actual executable is extracted as libmp4decrypt.so into nativeLibraryDir.
    Fix committed for 1.5.1:
      - At startup, create files/native/mp4decrypt as a symbolic link to the executable lib/arm64/libmp4decrypt.so in nativeLibraryDir.
      - This gives the old engine the exact filename and current-directory location it searches, while the symlink target remains on Android's executable native-library mount (not the app data noexec mount).
      - Run --help through the symlink itself and log/verify that its canonical target is the packaged executable.
      - Check the symlink again before starting each download.
    Status: Source fix committed; NOT yet runtime-verified. CI build and an encrypted MPD device download are still required. If the device rejects symlink execution, next step is to patch/rebuild the engine to honor DecryptionBinaryPath rather than claim success.
    Verification required: Successful encrypted MPD download on Android, not merely a successful APK build.

[ ] 4. Progress visibility / background execution.
    Changes committed for app version 1.5.2 (versionCode 17):
      - Download process moved out of MainActivity into DownloadService.
      - Service calls startForeground immediately and keeps an ongoing Downloads notification while the engine runs.
      - Notification updates with emitted engine output; percentage is shown when the engine emits a percent value, otherwise an indeterminate progress indicator is used.
      - Notification includes a Stop action; app Stop button controls the same service.
      - Runtime POST_NOTIFICATIONS permission is requested on Android 13+; if denied, Android may hide the notification from the drawer although the foreground service remains visible in system task manager.
      - Download process is no longer tied to Activity destruction, so it can continue when app is backgrounded. Android battery/vendor restrictions can still affect long-running transfers.
      - Signed URL query parameters are suppressed in notification text.
    Status: source changes committed; CI build and device background/notification test pending. Verify notification updates, Stop action, completion notification, and return to app log on device.

[ ] 5. False completion: notification said "Download complete. Published 0 file(s)" although logs stopped after stream selection and no media appeared.
    Root cause confirmed in app code: DownloadService treated process exit code 0 as success even when the output directory contained no media files; publishDownloads returned 0 for an empty directory.
    Changes committed:
      - Exit code 0 is no longer sufficient: require at least one non-empty recognized media file before showing success.
      - Metadata/empty folders are not published as media; empty output now produces an explicit failure diagnostic with output path and discovered file listing.
      - Pass an explicit writable cache subdirectory as --tmp-dir so segment staging does not depend on implicit runtime temp resolution.
    Status: source changes committed; CI and device retest pending. The user's log proves manifest parsing and stream selection only; it does not prove segment requests began.

[ ] 6. Android progress output was not interactive; the app saw only manifest parsing and selected streams.
    Root cause confirmed in upstream v0.6.0-beta source:
      - SimpleDownloadManager.StartDownloadAsync() uses Spectre.Console Progress with TaskDescription, ProgressBar, MyPercentageColumn, DownloadStatusColumn, DownloadSpeedColumn, RemainingTime and Spinner columns.
      - MyPercentageColumn renders the exact per-track counter as "Value/MaxValue NN.NN%".
      - The previous ProcessBuilder pipe made Console.IsOutputRedirected true, so the engine's interactive terminal renderer was not reliably available to Android.
    Changes committed:
      - Added a small Android Bionic PTY runner (posix_openpt/grantpt/unlockpt/fork/setsid/TIOCSCTTY) which launches the original ARM64 engine with stdin/stdout/stderr attached to a real pseudo-terminal and relays the terminal byte stream to Android.
      - Android DownloadService now launches the engine through libpty-runner.so rather than directly through a redirected pipe.
      - Parser strips ANSI CSI control sequences and extracts upstream's real per-track "Value/MaxValue NN.NN%" counters; it combines the selected video/audio counters into a weighted segment percentage.
      - App and foreground notification display video/audio segment counts and combined percentage.
      - APK verification and Gradle payload checks require the PTY runner.
    Status: implementation committed; CI build and Android device test pending. PTY output and segment-counter parsing must be verified on device before calling this resolved.

[ ] 7. Android progress parser showed incorrect audio total (100) when Spectre.Console emitted a percent-based denominator.
    Changes committed:
      - Use selected stream metadata ("N Segments") as the authoritative per-track total, adding the DASH init segment.
      - When Spectre reports a 0..100 denominator, scale the displayed completed count from the engine's percentage rather than reporting 0/100 segments.
      - Added .github/workflows/diagnose-mpd.yml: manual Linux x64 reproduction using the exact upstream v0.6.0-beta engine, FFmpeg, Bento4 mp4decrypt, the same 240p video/audio selection, key, retries and HTTP timeout.
      - The diagnostic workflow accepts only repository Actions secrets NM3U8_TEST_MPD_URL and NM3U8_TEST_KID_KEY; output is sanitized (MPD query strings and key material redacted) and only the sanitized log is retained for 3 days. No media output is uploaded.
    Status: implementation committed; Android APK CI and a user-triggered protected-MPD reproduction are pending. The repeated stop at 29 segments remains unresolved until the diagnostic log identifies the failing request.
